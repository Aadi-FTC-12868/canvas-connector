# Student app workflow inventory

Reviewed **2026-11-02 UTC** against the public connector working tree, including advanced Inbox authoring/controls and the optional personal tunnel adapter. The target is the student's full usable Canvas workflow, not a feature list inferred from the tools already implemented. The numbered rows below are a finite acceptance ledger; add a row when a newly verified student workflow is discovered rather than silently narrowing the target.

The baseline is the union of the official [Canvas iOS guide](https://community.instructure.com/en/kb/canvas_mobile-app-ios-guide) and [Android guide](https://community.instructure.com/en/kb/canvas_mobile-app-android-guide), with student web/API extensions explicitly identified. Native-app behavior does not establish that a third-party OAuth client can reproduce every operation. Admin masquerading, grading other students, and course administration are outside this student scope.

Implementation evidence is [tools.py](../src/canvas_connector/tools.py), [actions.py](../src/canvas_connector/actions.py), [student_actions.py](../src/canvas_connector/student_actions.py), [module_progress.py](../src/canvas_connector/module_progress.py), [personal_files.py](../src/canvas_connector/personal_files.py), [group_content.py](../src/canvas_connector/group_content.py), [preferences.py](../src/canvas_connector/preferences.py), [enrollments.py](../src/canvas_connector/enrollments.py), [bookmarks.py](../src/canvas_connector/bookmarks.py), [what_if_grades.py](../src/canvas_connector/what_if_grades.py), [mastery_paths.py](../src/canvas_connector/mastery_paths.py), [group_memberships.py](../src/canvas_connector/group_memberships.py), [discussion_attachments.py](../src/canvas_connector/discussion_attachments.py), [feedback.py](../src/canvas_connector/feedback.py), [appointments.py](../src/canvas_connector/appointments.py), [self_profile.py](../src/canvas_connector/self_profile.py), [dashboard_cards.py](../src/canvas_connector/dashboard_cards.py), [inbox_state.py](../src/canvas_connector/inbox_state.py), [inbox_messages.py](../src/canvas_connector/inbox_messages.py), [inbox_attachments.py](../src/canvas_connector/inbox_attachments.py), [page_views.py](../src/canvas_connector/page_views.py), [discussion_edits.py](../src/canvas_connector/discussion_edits.py), [group_files.py](../src/canvas_connector/group_files.py), and [group_file_uploads.py](../src/canvas_connector/group_file_uploads.py). A bundled library method does not count as an exposed workflow. “Implemented” below means the specified bounded operation exists; institution-specific live verification is separate and recorded in [VALIDATION.md](VALIDATION.md).

## Read the status correctly

- **Implemented:** a public tool handles the stated workflow, within the listed bounds.
- **Partial:** some of the workflow is implemented; the remaining work is named.
- **Not implemented:** connector code is missing. A documented API is a development opportunity, not an already-working capability.
- **External/client:** completion needs a browser, another service, or native client functionality. Any missing launch/discovery integration remains a connector gap.

**OAuth-gated and policy-gated are independent of these statuses.** An implemented operation can fail because the institution has not enabled the developer key or exact upstream scopes, the user's grant lacks write access, or Canvas denies the enrollment/resource operation. Conversely, approving more scopes cannot implement a missing handler. Preserve actual forbidden, locked, initial-post-required, and unavailable results. See [Canvas developer keys](https://developerdocs.instructure.com/services/canvas/oauth2/file.developer_keys) and [CANVAS-SCOPES.md](CANVAS-SCOPES.md). The runtime word `unsupported` describes the current adapter's boundary; it must not be translated into “Canvas has no API.”

## Next bounded implementation slices

These are ordered implementation candidates, not delivered capabilities or dates. Each slice needs a public tool/action contract, exact upstream scope manifest, ownership/policy checks, independent readback, failure/continuation behavior, and protocol tests before its row changes status.

1. **Group contexts and attachments (20/23/24):** attachment-preserving discussion edits are implemented. Permission-aware page editing still needs reliable editor-format eligibility; native viewing is separate. Shared group-file management/upload is implemented with explicit audience, native rights and visibility review; recursive deletion and cross-context transfers remain separate.
2. **Additional membership and progression (07/22):** explicit group switching, leadership changes, account-community groups and any supported invitation-response API need distinct review/readback. Mastery Path reselection is a separate adapter extension.
3. **Dashboard and file delivery (03/35):** native card ordering is implemented; active widget/K5 view integration and bounded original-file artifacts/offline export remain. Notification/channel lifecycle and optional bulk changes should be scoped separately from single-setting preferences.
4. **Appointments and personal profile (31/36), then calendar extensions (30):** self and student-group booking workflows, selected profile reads, names and five settings are implemented. Add regional settings, avatar upload/selection with moderation-aware verification, and any separately reviewed multi-booking replacement workflow. Keep group/all-day/recurring calendar operations distinct from personal timed events.
5. **Complete communication/planning details (16/26/29):** Inbox attachments, forwarding, selective audiences, markers and own-view deletions are implemented. Whole-history addition needs explicit authorization for potentially unseen/deleted history and honest coverage. Add linked/unscheduled notes and optional individual feedback-item markers.
6. **Assessment and external-launch work (12–14/17/39–42):** first separate Classic Quiz, New Quizzes, Student Annotation, media, and LTI contracts. Implement documented Classic Quiz/sessionless-launch portions with explicit lifecycle and school-policy handling; retain a browser/provider handoff where a supported learner API has not been established. Do not bypass proctoring, access codes, release restrictions, or provider authentication.

The gaps above remain open even when the current tool registry and automated tests are green. Closing the overall app-parity objective requires implementing or explicitly resolving every applicable workflow, with client/provider boundaries stated precisely and institutional validation recorded.
