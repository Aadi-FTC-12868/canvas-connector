# Student app workflow inventory

Reviewed **2026-11-02 UTC** against the public connector working tree, including comment attachments and module progress. The target is the student's full usable Canvas workflow, not a feature list inferred from the tools already implemented. The numbered rows below are a finite acceptance ledger; add a row when a newly verified student workflow is discovered rather than silently narrowing the target.

The baseline is the union of the official [Canvas iOS guide](https://community.instructure.com/en/kb/canvas_mobile-app-ios-guide) and [Android guide](https://community.instructure.com/en/kb/canvas_mobile-app-android-guide), with student web/API extensions explicitly identified. Native-app behavior does not establish that a third-party OAuth client can reproduce every operation. Admin masquerading, grading other students, and course administration are outside this student scope.

Implementation evidence is [tools.py](../src/canvas_connector/tools.py), [actions.py](../src/canvas_connector/actions.py), [student_actions.py](../src/canvas_connector/student_actions.py), and [module_progress.py](../src/canvas_connector/module_progress.py). A bundled library method does not count as an exposed workflow. “Implemented” below means the specified bounded operation exists; institution-specific live verification is separate and recorded in [VALIDATION.md](VALIDATION.md).

## Read the status correctly

- **Implemented:** a public tool handles the stated workflow, within the listed bounds.
- **Partial:** some of the workflow is implemented; the remaining work is named.
- **Not implemented:** connector code is missing. A documented API is a development opportunity, not an already-working capability.
- **External/client:** completion needs a browser, another service, or native client functionality. Any missing launch/discovery integration remains a connector gap.

**OAuth-gated and policy-gated are independent of these statuses.** An implemented operation can fail because the institution has not enabled the developer key or exact upstream scopes, the user's grant lacks write access, or Canvas denies the enrollment/resource operation. Conversely, approving more scopes cannot implement a missing handler. Preserve actual forbidden, locked, initial-post-required, and unavailable results. See [Canvas developer keys](https://developerdocs.instructure.com/services/canvas/oauth2/file.developer_keys) and [CANVAS-SCOPES.md](CANVAS-SCOPES.md). The runtime word `unsupported` describes the current adapter's boundary; it must not be translated into “Canvas has no API.”

## Next bounded implementation slices

These are ordered implementation candidates, not delivered capabilities or dates. Each slice needs a public tool/action contract, exact upstream scope manifest, ownership/policy checks, independent readback, failure/continuation behavior, and protocol tests before its row changes status.

1. **Files and folders (34), plus missing read detail (05/27):** expose `GetFolder`, `GetUserQuota`, file content-type filtering, and module prerequisite/sequential fields. Then add personal-folder creation and folder-targeted upload before destructive file management. The bundled seams are [files.py](../packages/canvas-py/src/canvas_py/endpoints/files.py), [file_uploads.py](../packages/canvas-py/src/canvas_py/endpoints/file_uploads.py), and [navigation.py](../packages/canvas-py/src/canvas_py/navigation.py). Preserve submitted-file restrictions and avoid a generic filesystem/API tool.
2. **Group contexts and discussion authoring (19/20/23):** use a typed course-or-group target, bounded membership-aware reads, new-topic creation without teacher fields, then real multipart attachment handling. Existing course-post permission should not silently authorize group writes or topic deletion. Group/topic creation endpoints are not already bundled implementations.
3. **Notification and dashboard preferences (03/28):** add own-channel/preferences discovery, single-setting reviewed updates, favorites/nicknames/colors. Separate notification suppression and profile changes from coursework submission permissions. No arbitrary user-setting dictionary.
4. **Appointments and personal profile (31/36), then calendar extensions (30):** discover only reservable slots, bind the exact slot/participant/time in review, and verify the student's reservation. Keep cancellation/rescheduling explicit; add self-profile/avatar operations with returned policy checks. These need new typed endpoints, not widening the existing personal-event guard.
5. **Complete communication/planning details (16/26/29/38):** inbox attachment uploads, star/subscription controls, linked/unscheduled notes, bookmarks, and explicitly designed feedback read state. Reuse the verified upload-receipt pattern where the upstream storage context matches.
6. **Assessment and external-launch work (12–14/17/39–42):** first separate Classic Quiz, New Quizzes, Student Annotation, media, and LTI contracts. Implement documented Classic Quiz/sessionless-launch portions with explicit lifecycle and school-policy handling; retain a browser/provider handoff where a supported learner API has not been established. Do not bypass proctoring, access codes, release restrictions, or provider authentication.

The gaps above remain open even when the current tool registry and automated tests are green. Closing the overall app-parity objective requires implementing or explicitly resolving every applicable workflow, with client/provider boundaries stated precisely and institutional validation recorded.
